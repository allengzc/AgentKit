# Tests —— 断言怎么写

本目录只讲一件事：**怎么加一条有用的断言**。其余见[根规范](../AGENTS.md)。

全部测试在 `Tests/main.swift` 一个文件里：**33 组 / 590 项断言**，
离线、无窗口、无网络。`./run-tests.sh` 编译 `Sources/Core` + `Sources/Surfaces`
+ 两个 App 文件 + 这个文件。

**能测到的前提是逻辑在 `Surfaces` 里**（见 [`Sources/Surfaces/AGENTS.md`](../Sources/Surfaces/AGENTS.md)）。
如果一段逻辑你没法断言，问题多半不在测试，在它放错了层。

## 三个辅助

```swift
group("随包文件：结构化列表数据")            // 一组
check(condition, "会发生什么")               // 布尔
equal(actual, expected, "会发生什么")        // 相等
check(condition, "标签", "补充说明")         // 第三个参数是失败时额外打印的细节
```

## 写法

1. **断言消息写"会发生什么"，不写"测试通过"**：
   `"相对路径被按进程工作目录解析（这就是那个 bug 的形状）"` ——
   失败时人要能直接读懂，不用回去看代码。
2. **修 bug 必须带一条能复现它的断言**。不是"改完顺手加个测试"，是**先写出会红的
   那条**。例如"启动物不存在的可执行文件"这条：改之前它会让**测试进程**直接 abort
   （`readDataToEndOfFile` 抛的 ObjC 异常接不住），现在它保证那条路径永远不再崩。
3. **断言里写清"为什么是这个期望值"**，尤其是反直觉的：
   `expectation` 是空的 `args` 不该消失、空 `description` 也算缺失、
   大小写变体是不是同一个文件**取决于卷**（那就按文件系统的真实行为断言，
   而不是硬编码一个答案）。
4. **不要断言环境有关的东西**。曾经有一条测试直接读作者机器上的一个真实 skill 目录 ——
   既是隐私泄露，也是坏测试（换台机器就红）。改成生成夹具，顺带覆盖了
   "条目很多"这个分支。同理：路径用 `/Users/dev/...` 这类中性值，
   时间戳写死。
5. **覆盖"看起来不会发生"的输入**：空字符串、未闭合的标记、多标量字素
   （emoji ZWJ 序列、组合音标）、超大输出、超时、非零退出码。
   预览那次崩溃就藏在"反引号嵌在粗体里"这种输入里。

## 交付时说得清

- 哪些是**断言保证**的
- 哪些是**截图确认**的
- 哪些**没验**

三者混淆比"没测"更危险 —— 它会让人以为有保证。数量（590 项）不是重点，
"这 590 项覆盖了什么、没覆盖什么"才是。

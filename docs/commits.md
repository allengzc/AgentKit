# 提交信息规范

给**写提交信息的人**（包括 agent）看的。上层原则在[根 `AGENTS.md`](../AGENTS.md) §6；
这一页是**类型与范围清单的唯一出处**。

`Tools/check-commit.sh` 直接读下面两张表 —— 每张表的前后各有一行 HTML 注释把它们夹住
（在编辑器里看得见，渲染出来是隐藏的），所以**改表就是改规则**，
不存在"文档一套、脚本一套"这种必然漂移的写法。表的第一列必须是反引号包起来的裸词，
脚本按这个形状读；列顺序和列数随便改。
（这两行注释不写在这里，是因为标记文本一旦出现在正文里，只认"第一次出现"的解析器
就会从这一行开始读，把别的表也当成本表 —— 这类错误查起来极其费劲。）

## 一、只对之后的提交生效

仓库里此前的 **19** 条提交没有一条带清单里的类型前缀，标题全是中文散文
（`修 diff 确认页的布局崩坏`）。有两条看着像前缀 —— `AgentKit: …` 和 `i18n：…` ——
一条的词不在清单里，一条的类型词带数字（类型只认 ASCII 字母），两种都过不了 R1。
那是既成事实，**不重写历史**：`filter-branch` 或交互式 rebase
重写一个已经推出去、可能已经有人 clone 过的历史，代价远大于"标题不够整齐"这点收益。

- 脚本拦的是**新提交**，`commit-msg` 钩子也只在提交那一刻运行 —— 历史不会被追溯
- 拿 `check-commit.sh` 对历史跑一遍：**19 条一条都过不了 R1**。这是预期基线，不是回归
- 反过来看，历史信息里"为什么 / 根因 / 怎么证"的写法**正是要保住的东西**：
  那 19 条的正文一个字都不用改，缺的只是一个前缀
  （试过一遍：`fix(views): …` 配上 `f8b07e9` 的原文，正文原封不动就是合规的）

## 二、一条消息长什么样

```
<类型>(<范围>): 一句话说清为什么

正文：根因是什么、怎么证的、为什么不选另一条路
```

- **标题**说**为什么**改，不说改了什么。改了什么 `git show` 里有，标题再抄一遍
  只是让读者多读一遍已经知道的东西
- **正文**写根因、证据（断言 / 截图 / 日志）、取舍。正文不是流水账 ——
  别写"先改了 A 再改了 B"，写"为什么非这么改不可"
- 分隔符 `：` 和 `:` 都认，大小写都认（`Fix:` 等同 `fix:`）。中文输入法下切来切去
  只会让人干脆不写前缀，那是本末倒置

## 三、类型

<!-- check-commit: types -->
| 类型 | 什么时候用 | 仓库里的真实例子 |
|---|---|---|
| `feat` | 新能力：新面板、新 agent、新描述文件字段、新的用户可见开关 | `966c340` 支持 Codex、`fa8b6fa` 适配 Claude Code、`3719ec7` 项目作用域从死路变成可达 |
| `fix` | 修 bug。**必须有正文**，写根因和怎么证的 | `3dc92dc` 修预览崩溃（根因：多趟正则各自把原文 range 换算成 attributed range，code 那趟先改短了，bold 那趟拿旧偏移就越界）、`cd36808` 修截图侧栏空白（根因：改成 `CALayer.render` 自渲染抓图，而侧栏材质由窗口服务器合成、根本不在图层树里） |
| `refactor` | 不改行为地搬动代码、重划边界。本仓库最典型的一种：**把逻辑从 `Views` 搬进 `Surfaces`** | `3dc92dc` 里"把纯文本逻辑从 Views 抽到 `Sources/Surfaces/MarkdownText.swift`"那一步 † |
| `docs` | 只改文档：`AGENTS.md`、`README*.md`、`docs/**` | `f560705` 写规范（根 + 五个分目录） |
| `test` | 只改 `Tests/main.swift` 的断言 | `f8b07e9` 里新增的那一组行号断言（双栏行号必须和真实文件逐行对得上）† —— 断言在这个仓库历来跟着被证明的改动一起走 |
| `chore` | 清理、改名、去真实数据之类的杂事 | `4c265cb` / `9c67c7d` / `9fb6bdd` 三条「清理」 |
| `perf` | 纯性能改动，正文要给出量出来的对比，不是"感觉更快了" | `3dc92dc` 把多趟正则换成单遍扫描那一段 † |
| `build` | 构建、打包、安装链路：`build.sh` / `install.sh` / `Resources/App-Info.plist` | `cf5c44f` 里"build.sh 会构建 `Tools/bin` 下的小工具、拷图标进包，图标缺失时直接报错"那部分 † |
<!-- /check-commit: types -->

† 这四条在历史上**没有独立的提交**（那次改动同时是别的事，比如 `test` 的断言总是搭在
产生它的那次改动上）。那一列写的是最接近的真实出处，用来给"这类改动长什么样"一个样本，
不是为了凑满类型而编的例子。真出现纯这一类改动时，直接用对应的类型。

**历史标题 → 类型**的对照，用来把老习惯接上新词：

| 历史里怎么写 | 现在用 | 例子 |
|---|---|---|
| 支持 XX / 适配 XX / 首个提交 | `feat` | `966c340`、`fa8b6fa`、`f0d2f49` |
| 修 XX / 修 XX 崩溃 | `fix` | `d3a7ebf`、`3dc92dc`、`cd36808` |
| 清理 | `chore` | `4c265cb`、`9c67c7d`、`9fb6bdd` |
| 写规范（只动 `.md`） | `docs` | `f560705` |
| `i18n` 打头（`i18n：…` / `i18n 基础设施…`） | `feat(i18n)` / `fix(i18n)` | `941a795`、`159973d` |

`i18n` 在历史里当前缀用过，现在它是**范围**不是类型：i18n 说的是改动的**战场**，
而"这次是加能力、修漏翻，还是搬键"只有类型说得清。

## 四、范围（可选）

范围说清**这次改动的主战场**，**不写也行**。本仓库大多数提交同时动三四个目录
（一次修 bug 往往同时改 `Sources`、`Tests`、`README.md`），硬要挑一个范围，
挑出来的多半是个随手写的、将来 grep 不到的标签。写了就必须是这张表里的词：

<!-- check-commit: scopes -->
| 范围 | 覆盖什么 | 仓库里的真实例子 |
|---|---|---|
| `core` | `Sources/Core/**`：JSON/TOML 树、唯一写盘路径、路径解析、描述文件、进程 | `966c340` TOML 解析器、`a52424b` `AgentProcess` 崩溃 |
| `surfaces` | `Sources/Surfaces/**`：各面板的纯逻辑（无 UI） | `3dc92dc` `MarkdownText` 落到这一层 |
| `views` | `Sources/Views/**`：SwiftUI 界面 | `f8b07e9` diff 确认页、`6e3c367` 换 `DisclosureGroup` |
| `app` | `Sources/App/**`：状态、项目作用域、写入控制器 | `3719ec7` 新增 `ProjectStore`，项目作用域这才可设置（`projectURL` 反而是只读计算属性） |
| `agents` | `Resources/Agents/*.json`：内置描述文件 | `966c340` `codex.json`、`fa8b6fa` `claude.json` |
| `assets` | `Resources/Icon*.svg`、`AppIcon.icns`、`App-Info.plist` | `cf5c44f` 图标问系统要连续曲率圆角 |
| `i18n` | `Resources/Localization/**`，以及 `LocalizedText` / `L.t` 的跨层改动 | `159973d` i18n 基础设施、`941a795` 界面、消息、描述文件、设置表全双语 |
| `tools` | `Tools/**`，以及根下的 `build.sh` / `install.sh` / `run-tests.sh` | `a52424b` 夹具与截图脚本、`cf5c44f` `make-icon.py` |
| `tests` | `Tests/main.swift` | `d3a7ebf` 的 `PathResolver.isSameFile` 断言 |
| `docs` | `docs/**`、`README*.md`、各目录的 `AGENTS.md` | `f560705` 根 + 五个分目录的 `AGENTS.md`、`3468809` `docs/` 下的图 |

范围**不做"路径必须匹配"的交叉检查**：逻辑不许长在 `Views` 里（[根规范 §3](../AGENTS.md)），
所以一个 `fix(views)` 的改动落在 `Sources/Surfaces` 才是对的 —— 拿路径去断定范围属于哪一层，
正好会惩罚这个仓库最想鼓励的那件事。

## 五、必须有什么，不要求什么

**必须**：

| 要求 | 谁在管 |
|---|---|
| 说清**为什么**改，而不是改了什么 | 人 —— 这是判断，不是格式 |
| 说清**怎么验证**的（断言 / 截图 / 日志） | 人 —— 同上 |
| 修 bug 的必须写**根因** | 人写；机器只能保证"`fix` 有正文"（R5），写没写对不查 |
| 标题有类型前缀，且类型在清单里 | 机器 R1 |
| 范围（若写了）在清单里 | 机器 R2 |
| 标题不是空壳（前缀后面有话说） | 机器 R3 |
| 标题是中文 | 机器 R4 |
| 行为类改动（`feat` / `fix` / `refactor` / `perf`）必须有正文 | 机器 R5 |
| `docs` 必须真的改了 `docs/**` 或 `*.md` | 机器 R6（只在能读到暂存区时） |

**不要求**，以及为什么：

- **标题长度上限**：不设。量过：仓库 19 条标题中位数 23 字、最长 40 字，没有失控的迹象；
  而常见的"50 字符"上限在中文里是按字节算的（一个汉字 3 字节），实际只能写 16 个字 ——
  它拦下的全是**正确**的提交。标题长短是审美，不是正确性
- **每条都要正文**：只有"改变行为"的类型要正文（`feat` / `fix` / `refactor` / `perf`）。
  一个文档错别字、一次 `chore` 改名，正文只能是重复标题，逼出来的是噪音
- **正文用中文**：不要求。正文经常要贴英文报错、栈、命令 —— 那正是它该有的样子
- **结尾不要句号、要用祈使句、正文每行 72 列**：不要求。这套规则来自英文 commit 习惯，
  中文里没有对应的收益，只会增加"我是不是又写错了"的焦虑
- **一次提交一件事**：这条是[根规范 §6](../AGENTS.md)的要求，但**查不了** ——
  "一件事"的边界是人判断的，机器一查必然误报
- **"为什么"写得够不够好**：查不了，也不该假装能查。关键词白名单（要求出现"根因""复现"）
  看起来能查，实际上会把"因为这个偏移量已经过期"这种正确写法判错，而把抄了"根因：无"
  的判对 —— 一个专拦正确提交的钩子，下场就是所有人都加 `--no-verify`

## 六、机器怎么查

```bash
Tools/check-commit.sh .git/COMMIT_EDITMSG        # 给一个消息文件
git log -1 --format=%B | Tools/check-commit.sh   # 或从 stdin 读
Tools/check-commit.sh --no-paths 老消息.txt      # 跳过 R6（拿历史消息试跑时有用）

./Tools/install-hooks.sh                # 装 commit-msg 钩子（每个 clone 装一次）
./Tools/install-hooks.sh --status       # 看装没装
./Tools/install-hooks.sh --uninstall    # 卸掉
```

其余开关（`-q` 等）看 `Tools/check-commit.sh --help`。钩子装在 `.cache/hooks/`（.gitignore 里
已忽略），由 `core.hooksPath` 指过去 —— **不写 `.git/hooks/`**：那个目录不进版本控制，
钩子放进去就没人知道它从哪来。

| 规则 | 内容 | 不通过时 |
|---|---|---|
| R1 | 标题是 `<类型>(<范围，可省>): 内容`，类型在清单里 | 报错，并列出清单 |
| R2 | 写了范围就必须在清单里 | 报错，并列出清单 |
| R3 | 标题不能只有前缀（`feat:` 后面得有话说） | 报错 |
| R4 | 标题至少有一个汉字 | 报错（用 `python3` 判；没有 python3 时**跳过这条**并说明，不拦提交） |
| R5 | `feat` / `fix` / `refactor` / `perf` 必须有正文 | 报错 |
| R6 | `docs` 类型必须真的动了 `docs/**` 或 `*.md` | 报错，只在能读到暂存区时检查 |

规则里唯一一处硬编码清单是 R5 的四个类型（脚本里的 `BODY_REQUIRED`）—— 它没有自己的表。
要动它得同时改那个变量和这一页 §五 / §六 的说法；类型表和范围表不需要这样，它们只有一处。

豁免：标题以 `Merge ` / `Revert "` / `fixup!` / `squash!` 开头 → 直接通过。
这些是 git 自己生成的消息，格式不归人管。

退出码：`0` 通过、`1` 不合规、`2` 检查脚本自己读不到输入（比如 `docs/commits.md`
的类型表被改坏了）—— `2` 单独分开，是为了让"钩子坏了"和"消息错了"不混为一谈。

**为什么没挂进 `run-tests.sh`**：那是离线断言套件，验的是产品行为，和 git 历史无关；
把提交检查塞进去，会让"在不是 git 仓库的目录里跑断言"变成一个假失败，
也会让改一条断言先要看提交信息。提交检查只在**提交那一刻**有意义。

规范与代码不一致时：**指出来**，别默默照其中一方做。这一页本身也可以被质疑和修改。

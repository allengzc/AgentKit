# Sources/Surfaces —— 逻辑层的边界

本目录只讲一件事：**什么代码该放在这里**。其余见[根规范](../../AGENTS.md)。

各面板的纯逻辑，没有 UI：合并、解析、校验、字段表、扫描。
`10 个文件 ≈ 2900 行`，全部会被 `run-tests.sh` 编译进测试二进制 ——
**这一层唯一的特权就是"测得到"，也正因为如此，它是唯一能保证行为正确的地方。**

## 判据

要判断 / 计算 / 解析的 → **放这里**。
决定长什么样、放哪、什么颜色 → **放 Views**。

拿不准就问：**这段能不能写成一条断言？** 能，那它不属于 Views。

## 硬性要求

1. **不 import SwiftUI**，唯一例外是 `MarkdownText.swift` —— 它要给
   `AttributedString` 设字体，而字体属性的作用域由 SwiftUI 提供。除此之外
   这一层不许碰 UI 框架。
2. **新增的 `*Spec` 字段必须可有默认值**。描述文件是别人写的、旧版本要能继续跑：
   `Descriptors/*.json` 里没有这个键时不能解析失败，行为要跟加字段之前一样。
   加完字段**跑一遍现有描述文件**确认三个 agent 都还正常。
3. **`SettingsSchema` 的字段表要么手写、要么由脚本生成**（生成的要带生成脚本，
   见 [`Tools/AGENTS.md`](../../Tools/AGENTS.md)）。不要"照记忆补几个键" ——
   字段表的价值就在于它和上游文档对得上。
4. **面板处理器是封闭集合**。描述文件能引用的是那 7 个 `kind` / 形状；
   要加第 8 个，先确认不是现有形状缺一个字段（根规范 §1）。
   不认识的形状要降级成占位符，**不许崩**。

## 一条踩过的

`MarkdownText` 原来长在 `Views/Components/MarkdownEditorView.swift` 里。
它用两趟正则改同一个 `AttributedString`，第二趟拿的是**原文的偏移量** ——
遇到"反引号嵌在粗体里"（`**优先使用 \`exa\`**`）就越界，`replaceSubrange` 直接 abort，
**崩在用户点"预览"的时候**。抽到这里之后，那条输入现在是测试用例。

结论不是"要小心正则"，是：**测不到的代码会带病到用户手上**。
